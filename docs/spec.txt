Physics-Based RealtimeMultiplayer 2D Canvas
Product specification and technical implementation plan
Target: browser/PWA client in TypeScript + existing Go backend
Core architecture decision
[BodyText] Physics stays off the server. One elected client acts as the room simulation host. The Go service coordinates the room, grants a single host lease, relays realtime traffic in the first implementation, enforces ownership, and stores periodic canonical snapshots. Other clients predict only their own avatar and interpolate shared state.
Prepared from project requirements and architecture interviewAugust 21, 2026

[Heading1] Executive summary
[BodyText] This system is a persistent, shared 2D world for up to 20 active avatars and about 50 items. Avatars are circular, player-controlled entities. Items may be decorative, sensor-only, static collision geometry, simple movable bodies, or developer-authored interactive objects with multi-step behaviors. A canvas defines world geometry, edge rules, environmental forces, rendering orientation, and item tuning.
[BodyText] The recommended architecture uses one client as the canonical simulation host for each active canvas. That host runs the full physics and behavior model in a Web Worker. Other clients send control intent, predict their own avatar, and render shared entities from host snapshots. The Go backend never steps physics. It grants a host lease, prevents split-brain authority, validates durable mutations and ownership, relays packets for the first implementation, and stores checkpoints for persistence and host migration.
[BodyText] Start with secure WebSockets because they are simple, observable, and backend-agnostic. Keep the transport behind an interface. If relay bandwidth later matters, add a WebRTC star topology from the simulation host to other clients. Do not start with a full peer mesh.

[Heading1] 1. Product goals and non-goals
[Heading2] 1.1 Goals
[ListBullet] Make a shared 2D canvas feel immediate and playful on phones and desktop browsers.
[ListBullet] Support objects that react to one or more avatars, other items, collisions, bounces, timers, regions, and workflow state.
[ListBullet] Allow one item to have multiple collision shapes with different roles: solid contact, interaction sensors, triggers, and hit areas.
[ListBullet] Support top-down and side-facing worlds from the same runtime.
[ListBullet] Support spatially varying forces and drag, including smooth gradients.
[ListBullet] Keep realtime physics CPU off the Go backend.
[ListBullet] Persist the scene so item position, rotation, ownership, configuration, and durable state survive an empty room.
[ListBullet] Allow item owners to spawn, move, rotate, configure, and delete only their own items.
[ListBullet] Keep behavior authoring extensible without allowing arbitrary user scripting.
[ListBullet] Allow transport to evolve from WebSocket relay to WebRTC without rewriting gameplay code.
[Heading2] 1.2 Non-goals for the first implementation
[ListBullet] Competitive anti-cheat or tamper-proof physics. A malicious simulation host can influence outcomes. The system will stop unauthorized durable edits, but it will not prove every physical interaction.
[ListBullet] Rollback netcode or frame-identical deterministic simulation on every client.
[ListBullet] A user-facing visual behavior editor.
[ListBullet] Large MMO-scale rooms, hundreds of simultaneous dynamic bodies, or server-side always-on worlds.
[ListBullet] General 3D physics. Top-down “height” uses a lightweight 2.5D elevation channel rather than a 3D rigid-body engine.
[ListBullet] Offline continuation. An empty canvas sleeps.

[Heading2] 2.1 Core concepts

[Heading2] 2.2 Coordinate system and units
[BodyText] Use logical world units, not pixels, for all simulation data. A canvas might be 100 x 60 world units regardless of whether it renders into a 390 px phone viewport or a 1600 px desktop viewport. The camera maps world units to screen pixels. This keeps item behavior stable across screen sizes and lets a canvas tune items based on world dimensions rather than device resolution.
[ListBullet] Origin: top-left is acceptable for rendering, but physics APIs should expose a consistent world-space convention. Recommended: X increases right, Y increases down to match browser canvas coordinates.
[ListBullet] Rotation: radians internally; degrees only in authoring UI.
[ListBullet] Time: fixed simulation ticks, not frame time, for behavior timers.
[ListBullet] Scale: item definitions use world-unit dimensions. Sprite assets can have any source pixel size.
[ListBullet] Persistent transforms: X, Y, rotation, optional elevation Z. Velocities are not resumed after room sleep by default.

[Heading2] 3.2 Edge policies
Policy
Behavior
solid
A fixed world collider prevents bodies from leaving.

Crossing one edge teleports the body to the opposite edge while preserving velocity and rotation.

[BodyText] Configure each edge independently. A soccer-field-style canvas could be solid on all sides. A looping space canvas could wrap horizontally and vertically. A platform canvas could be solid on the sides, open at the bottom, and respawn fallen objects at center.
[Heading2] 3.3 Static geometry
[BodyText] Static collision geometry belongs to the canvas rather than being stored as ordinary user-owned items. It includes floors, walls, hills, ramps, launch pads, barriers, and collision-only shapes that do not need per-instance ownership. Static geometry may still expose semantic tags such as hill, launchPad, goal, or wall so behavior logic can react to contacts.
[ListBullet] Prefer primitive shapes and convex polygons.
[ListBullet] Use several convex colliders instead of one complicated concave polygon when practical.
[ListBullet] Allow sensor-only static geometry for zones that should trigger events without blocking motion.
[ListBullet] Keep the rendered background separate from collision geometry so art can change without altering physics.
[Heading1] 4. Environmental physics and 2.5D elevation
[Heading2] 4.1 Environment fields
[BodyText] Do not model canvas physics as a single global gravity vector. Instead, sample an environment field for each affected body during each simulation step. The field starts with canvas defaults and blends in region modifiers. This gives the rocket example a natural implementation: full downward gravity near the ground, a smooth reduction in gravity through the upper canvas, increased drag or a soft speed cap in “space,” then stronger downward acceleration as the rocket returns.
interface EnvironmentSample {  gravityXY: Vec2;  linearDrag: number;  angularDrag: number;  softSpeedLimit?: number;  surfaceFrictionMultiplier: number;  // Optional top-down 2.5D channel.  zGravity: number;  zDrag: number;}interface RegionFieldModifier {  shape: RegionShape;  blend: "step" | "linear" | "smoothstep" | "radial";  priority: number;  gravityXY?: FieldValue<Vec2>;  linearDrag?: FieldValue<number>;  softSpeedLimit?: FieldValue<number>;  zGravity?: FieldValue<number>;}

[BodyText] Forces should usually be applied rather than teleporting or hard-clamping a body. A soft speed limit can add drag only to the velocity above a threshold. This produces smoother motion and fewer abrupt corrections across the network.
[Heading2] 4.2 Side-facing canvases
[ListBullet] Y gravity is the main gravity vector.
[ListBullet] Static geometry provides ground, ramps, hills, platforms, and walls.
[ListBullet] Air resistance uses linear and angular drag.
[ListBullet] Avatar movement uses horizontal/vertical intent but the canvas may constrain allowed movement if desired.
[ListBullet] Dynamic items may use restitution, friction, mass, gravity scale, and explicit designer forces.
[Heading2] 4.3 Top-down canvases
[ListBullet] The X/Y plane has little or no gravity. Drag gives rolling/sliding objects a natural slowdown.
[ListBullet] Optional elevation Z is simulated separately as scalar position/velocity.
[ListBullet] Z controls visual offset, scale, shadow separation, and whether an item participates in ground-level collisions.
[ListBullet] An item can be “kicked into the air” without requiring a 3D rigid-body world.
[ListBullet] When Z returns to the ground plane, emit a landing event and optionally an impact impulse or bounce.
Recommended 2.5D rule
[BodyText] Keep X/Y physics in Rapier and model Z as a small custom component. Do not introduce a 3D engine just to make top-down objects hop, arc, or fall.
[Heading1] 5. Physics and collision model
[Heading2] 5.1 Recommended physics engine
[BodyText] Use Rapier 2D in the browser, loaded as WebAssembly. It has rigid-body types, multiple colliders per body, sensor colliders, collision events, forces, impulses, sleeping, filtering, and fixed/static/kinematic/dynamic bodies. Those features map well to the required interaction model. The simulation host should run the physics world in a Web Worker so rendering and touch input remain responsive.

[Heading2] 5.3 Collision roles and layers
[BodyText] An item is not limited to one collision box. It may have several colliders attached to the same rigid body, each with its own role and filter. For example, a rocket can have a narrow solid hull, a larger “touch to arm” sensor, and a small launch-pad alignment sensor.

[Heading2] 5.4 Passing through versus kicking
[BodyText] Separate “can overlap” from “can interact.” If an avatar should pass through an item, exclude AVATAR_BODY from that item’s solid collision mask but keep its interaction sensor active. The behavior still receives touch events. If an item should be kickable, either allow the avatar body to contact it physically or use a sensor-based Kickable behavior that applies a capped impulse based on avatar velocity and contact direction.
kickImpulse = clamp(  kickStrength * max(0, dot(avatarVelocity - itemVelocity, contactNormal)),  minImpulse,  maxImpulse);applyImpulse(item, contactNormal * kickImpulse);

[BodyText] The sensor-based kick option is useful when the designer wants the avatar to glide through the item while still making it move. A short per-avatar/item contact cooldown prevents one overlap from applying an impulse on every physics tick.
[Heading1] 6. Avatar controls and local prediction
[Heading2] 6.1 Input model
[BodyText] Treat touch and click-drag as movement intent, not as authoritative position. The input layer turns a drag vector into desired direction and magnitude. The avatar controller then accelerates toward a desired velocity with a configured maximum speed and acceleration. This keeps collisions meaningful and prevents a pointer jump from teleporting through walls.
[ListBullet] Pointer/touch down establishes a drag origin or virtual joystick center.
[ListBullet] Drag vector maps to normalized direction and 0..1 intensity with a dead zone.
[ListBullet] Release decelerates to zero using avatar drag or explicit braking.
[ListBullet] Send input sequence number, desired direction, intensity, and client-local input time.
[ListBullet] Do not send raw avatar position as normal control data.
[Heading2] 6.2 Prediction and reconciliation
[BodyText] Every client predicts only its own avatar against local static canvas geometry. The simulation host also simulates that avatar as part of the canonical world. Host snapshots include the last processed input sequence for each avatar. The local client compares the canonical position with its prediction and reconciles the difference.
[ListBullet] Small error: blend the correction over several render frames.
[ListBullet] Large error or invalid geometry penetration: snap to the canonical position.
[ListBullet] Remote avatars: interpolate from buffered host snapshots; do not predict their controls.
[ListBullet] Shared physics items: interpolate/extrapolate visually; do not run competing canonical item physics on non-host clients.

[Heading2] 7.2 Item instance
interface ItemInstance {  entityId: string;  canvasId: string;  definitionId: string;  definitionVersion: number;  ownerUserId: string;  transform: { x: number; y: number; rotation: number; z?: number };  resolvedConfig: unknown;  behaviorState?: unknown;  createdAt: string;  sceneRevision: number;}

[Heading2] 7.3 Canvas-aware tuning
[BodyText] Item definitions should not hard-code one set of physics values for every canvas. Each definition may include data-only tuning rules that resolve configuration when the item is spawned or when a canvas version changes. The resolved result is stored on the instance so every client receives the same values.
tuningRules: [  {    when: { maxCanvasWidth: 70 },    overrides: { scale: 0.85, thrust: 18, maxSpeed: 14 }  },  {    when: { minCanvasWidth: 70 },    overrides: { scale: 1.0, thrust: 24, maxSpeed: 19 }  }]

[BodyText] This keeps the behavior developer-authored while letting the same rocket, ball, portal, or toy feel right on differently shaped canvases. Keep the tuning language small and declarative so the backend can validate it without running game code.
[Heading1] 8. Extensible behavior and workflow system
[Heading2] 8.1 Design principle
[BodyText] Behavior code should consume events and emit commands. It should not reach directly into PixiJS, WebSocket objects, persistence, or arbitrary global state. This boundary is the most important extensibility decision in the design because it makes complex items testable, serializable, and transport-independent.
[Heading2] 8.2 Behavior API

Examples

Number or set of qualifying avatars/items currently touching a sensor.

[Heading2] 8.4 Behavior state rules
[ListBullet] State must be serializable data. No closures, DOM nodes, renderer objects, or physics handles in persisted state.
[ListBullet] Use simulation ticks for countdowns and durations while a room is active.
[ListBullet] Persistent behavior state must declare a schema version and migration function when it changes.
[ListBullet] Transient particle systems, trails, shakes, and sound are effect events, not persisted state.
[ListBullet] Process events in a stable order within a tick to make host behavior reproducible and easy to test.
[ListBullet] Apply commands after event handling rather than allowing behavior callbacks to mutate the physics world in arbitrary order.
[Heading2] 8.5 Rocket example
states:  idle    contactCount(avatar) >= 1 -> arming  arming    on enter: start countdown(3s), show countdown overlay    contact forces may still rotate/push rocket    timer.complete -> launch    no qualifying contact for configured grace -> idle  launch    apply thrust along rocket forward vector    start trail effect    -> flying  flying    region.enter("space") -> spaceDrift    contact("ground") at low speed -> landed  spaceDrift    use environment field: reduced gravity + drag + soft speed cap    region.exit("space", heading downward) -> falling  falling    environment field increases downward gravity as Y increases    contact("ground") -> landed  landed    zero excessive residual motion    short cooldown -> idle

[BodyText] The countdown overlay is derived from the authoritative activation tick and duration. Clients do not need a countdown packet every frame. The trail is a local effect triggered by a single launch event and stopped by behavior state change.
[Heading1] 9. Rendering and animation
[Heading2] 9.1 Recommended renderer
[BodyText] Use PixiJS 8 for the scene renderer. It maps naturally to sprite-heavy 2D worlds and separates rendering from the physics engine. Prefer the stable WebGL path for production. Keep rendering on the main thread and physics/behavior on a worker.
[ListBullet] Use texture atlases for item and avatar assets.
[ListBullet] Anchor sprites around the entity origin so rotation and collider alignment are predictable.
[ListBullet] Use animation definitions keyed by behavior state: idle, arming, launch, landed, etc.
[ListBullet] Pool particles and trail segments. Do not create network entities for cosmetic particles.
[ListBullet] Represent interaction overlays, ownership handles, countdowns, and selection rings in a separate UI layer.
[ListBullet] Interpolate display transforms independently from the canonical physics state so network jitter does not directly shake the sprite.

[Heading1] 10. Multiplayer architecture
[Heading2] 10.1 Why a single client simulation host
[BodyText] Do not give every client authority over its own physics objects, and do not let every peer simulate the same shared world and vote on results. Both approaches become difficult when two avatars touch the same item, an item hits another item, or a workflow depends on collision order. A single client simulation host gives the room one canonical answer without making the server run physics.
[ListBullet] One canonical collision order and behavior event stream.
[ListBullet] Simple handling of two players kicking the same object.
[ListBullet] No requirement for cross-browser floating-point determinism.
[ListBullet] Cheap host migration because scene state is small.
[ListBullet] Server CPU remains focused on I/O and validation rather than frame simulation.

[Heading2] 10.4 Snapshot interpolation
[BodyText] Clients keep a short buffer of host states and render remote entities slightly behind the newest packet. Start with about 100 ms of interpolation delay and tune from production metrics. Extrapolate briefly using linear/angular velocity if the next state is late, then stop extrapolating rather than letting an item drift indefinitely.
[Heading1] 11. Host election, leases, and migration
[Heading2] 11.1 Single host lease
[BodyText] The Go backend must be the authority for who is allowed to publish canonical state. Each room has a monotonically increasing hostEpoch and one active hostClientId. Every canonical state packet carries the current epoch. Peers ignore state from an old epoch. This prevents split-brain when an old host reconnects or a network hiccup causes two clients to believe they are host.
RoomAuthority {  roomId: string  hostEpoch: uint64  hostClientId: string  leaseExpiresAt: timestamp}

[Heading2] 11.2 Host selection
[BodyText] Keep election simple. Any compatible, foreground client can host. Prefer a client that is visible, has a stable connection, and has recently demonstrated a healthy simulation loop. The first client may become host immediately; later migrations can use health information.
[ListBullet] Host voluntarily yields when the page becomes hidden or its simulation worker falls materially behind.
[ListBullet] Backend revokes the lease when host heartbeats stop.
[ListBullet] Backend increments hostEpoch before assigning the replacement.
[ListBullet] New host starts from the freshest accepted keyframe/checkpoint and broadcasts a full state immediately.
[ListBullet] All clients clear stale interpolation history when hostEpoch changes.
[Heading2] 11.3 Host migration sequence
1. Host heartbeat expires or host sends YIELD_HOST.2. Backend marks old lease invalid and increments hostEpoch.3. Backend chooses a connected eligible client.4. Backend sends HOST_GRANTED(epoch, canonicalCheckpoint).5. New host builds full physics world from checkpoint.6. New host starts fixed-step simulation.7. New host sends FULL_STATE(epoch, tick=0 or resumedTick).8. Other clients resume interpolation and input routing.

[Heading2] 11.4 Browser backgrounding
[BodyText] A browser tab can throttle timers or suspend work when backgrounded, especially on mobile. Treat visibility changes as a host-health signal. The host should yield before the browser becomes unusable when possible. The backend should still rely on heartbeats because visibility events are not guaranteed during a crash or abrupt process kill.
[Heading1] 12. Transport and wire protocol
[Heading2] 12.1 V1 transport: secure WebSocket relay
[BodyText] Add one realtime WebSocket endpoint to the existing Go binary. Clients connect to the backend, join a room, and the backend relays realtime packets without interpreting physics. This is simple to deploy, works through common firewalls, keeps authentication in one place, and makes logging and host migration straightforward. At the expected room size, relay traffic should be modest.
Important
[BodyText] WebSocket relay still uses server bandwidth, but the expensive part - simulation and behavior execution - stays on a client. This is the recommended first implementation because it minimizes architecture risk.
[Heading2] 12.2 Optional later transport: WebRTC host star
[BodyText] Keep networking behind a RoomTransport interface. A later WebRTC implementation can create direct DataChannels from the simulation host to each peer. The Go backend continues to authenticate membership, exchange signaling data, grant the host lease, and receive durable checkpoints. Use WebSocket as a fallback because some connections will require TURN or may fail direct ICE negotiation.
interface RoomTransport {  connect(join: JoinDescriptor): Promise<void>;  sendReliable(message: ReliableMessage): void;  sendRealtime(message: RealtimeMessage): void;  onMessage(handler: (message: RoomMessage) => void): Unsubscribe;  close(): void;}

[BodyText] For WebRTC, use separate logical channels: a reliable ordered channel for control/state transitions and an unordered or limited-retransmit channel for frequent transform snapshots. Old transform packets are usually less useful than newer ones.
[Heading2] 12.3 Binary protocol
[BodyText] Use Protocol Buffers for realtime envelopes shared by TypeScript and Go. Keep JSON for editable item/canvas definitions and administration. Binary state packets are smaller and faster to parse, while versioned .proto files make the Go/TypeScript contract explicit.
message RoomEnvelope {  string room_id = 1;  uint64 host_epoch = 2;  uint32 sequence = 3;  uint64 tick = 4;  oneof payload {    PlayerInput player_input = 10;    StateDelta state_delta = 11;    FullState full_state = 12;    EffectEvent effect_event = 13;    HostControl host_control = 14;    DurableCommand durable_command = 15;    DurableCommandResult durable_result = 16;  }}

[Heading1] 13. Persistence and room sleep
[Heading2] 13.1 What is persisted
[ListBullet] Canvas version and scene revision.
[ListBullet] Item instance IDs, definition IDs and versions.
[ListBullet] Owner user IDs.
[ListBullet] Resolved item configuration.
[ListBullet] X/Y/rotation and optional elevation Z.
[ListBullet] Persistent behavior state that the item definition declares durable.
[ListBullet] Any persistent visual variant or mode needed to reconstruct the item.
[ListBullet] A canonical checkpoint revision and host epoch for recovery bookkeeping.
[Heading2] 13.2 What is not resumed after the room empties
[ListBullet] Linear and angular velocity.
[ListBullet] Active forces or impulses.
[ListBullet] Cosmetic particles and trails.
[ListBullet] Short-lived contact sets.
[ListBullet] Default transient behavior timers and mid-animation progress.
[ListBullet] Avatar entities; players are presence, not persisted world objects.
[Heading2] 13.3 Room sleep sequence
1. Last connected client leaves.2. Backend uses the newest canonical checkpoint.3. Normalize runtime motion: velocity = 0, angularVelocity = 0.4. For each item behavior:     resetToIdle -> call its room-sleep normalization rule.     pause       -> keep declared persistent state, but stop timers.5. Persist the normalized snapshot.6. Mark room SLEEPING.7. No simulation runs while the room is empty.

[BodyText] On a graceful final disconnect, the host sends one final checkpoint before leaving. If the host dies abruptly, the backend falls back to its most recent periodic checkpoint. With a 1 Hz checkpoint, sudden process death may lose up to about one second of movement. Increase checkpoint frequency only if product testing shows that this is visible enough to matter.
[Heading2] 13.4 Room wake sequence
1. First player joins a sleeping canvas.2. Backend loads normalized persisted snapshot.3. Backend grants host lease to an eligible client.4. Host rebuilds physics bodies with zero motion.5. Behaviors receive ROOM_WAKE and initialize transient state.6. Host publishes full state.7. Other clients join/interpolate from that state.

[Heading1] 14. Ownership, editing, and integrity
[Heading2] 14.1 Server-authoritative durable mutations
[BodyText] The simulation host is authoritative for moment-to-moment physics, but it is not authoritative for ownership or durable edits. Every spawn, delete, move-in-edit-mode, rotate, or config change goes through the Go backend. The backend checks the authenticated user and item owner before accepting the command.
owner client -> DURABLE_COMMAND(move item 123)Go backend:  authenticate user  load/check item owner  validate config / bounds / scene limits  increment sceneRevision  broadcast accepted commandsimulation host:  apply edit to canonical world  include result in next snapshot

[Heading2] 14.2 Edit mode behavior
[ListBullet] While the owner drags an item for editing, show a local ghost immediately.
[ListBullet] Send rate-limited edit updates through the reliable server path.
[ListBullet] The host applies the accepted transform as a kinematic reposition or temporary simulation lock.
[ListBullet] On release, the owner sends a final durable transform.
[ListBullet] Non-owners may interact with the item through its normal physics/behavior but cannot change its configuration or authored placement.
[Heading2] 14.3 Integrity limitations
[BodyText] Because physics runs on a player device, the host can potentially send fake physical outcomes. For a social canvas this is an acceptable tradeoff if physics is not tied to money, rankings, or safety. The backend should still reject malformed state, unknown entity IDs, impossible scene revisions, NaN values, grossly out-of-bounds transforms, and packets from a client without the active host lease.

[Heading2] 15.2 Worker boundary
[BodyText] The simulation worker owns Rapier handles, canonical behavior state when hosting, environment sampling, and fixed-step time. The main thread owns PixiJS, DOM/UI overlays, pointer/touch input, and transport objects. Send compact input/state messages across the worker boundary. Do not pass physics engine objects across it.
[ListBullet] Host client: worker contains the full room world.
[ListBullet] Normal client: worker may contain only static collision geometry plus the local avatar prediction world.
[ListBullet] Main thread receives render snapshots as typed arrays or small structured-clone objects.
[ListBullet] Avoid SharedArrayBuffer in V1; the cross-origin isolation requirements are not justified at this scale.

[BodyText] This is an ECS-like composition model, not a requirement to adopt a full ECS framework. A lightweight registry is enough for 70-ish active entities. The important part is avoiding deep class inheritance such as Rocket extends PhysicsItem extends Item extends SpriteEntity.

[Heading2] 17.1 Player joins an active room

[Heading2] 17.2 Avatar kicks a rocket
Player client  predicts avatar movement immediately  sends INPUT(seq=812, direction, intensity)        |        vSimulation host  applies input during fixed tick  avatar contact/sensor intersects rocket  Kickable -> impulse command  Rapier steps rocket  RocketBehavior receives contact/bounce events  host emits STATE_DELTA + effect/state changes        |        vAll clients  reconcile avatar if needed  interpolate rocket transform  render effect events locally

[Heading2] 17.3 Two avatars activate one item
[BodyText] The host maintains the canonical set of entities touching each interaction sensor. A behavior can query or receive contact-count changes. Because all contacts are evaluated in one world, “two avatars must touch this pad for 500 ms” is straightforward: record the qualifying avatar set, transition when its size reaches two, schedule the timer, and cancel if the count falls below two before completion.
[Heading2] 17.4 Portal / partial teleportation
[BodyText] Treat a portal as a sensor plus a behavior command, not as an edge case in the physics engine. The behavior can transform position and velocity through a portal mapping. For a partial portal visual, render the sprite into clipped masks on each side while the canonical body transitions based on a defined threshold. If true split-body physics is not required, keep one rigid body and make the “partial” effect visual.

[ListNumber] Profile the host worker and rendering independently.

[Heading2] 19.3 Suggested network budget
[BodyText] Design for an average of less than roughly 20 KB/s of realtime state per receiving client in a busy scene. With only avatars and a handful of moving items in each transform packet, the expected payload should be comfortably below that after binary encoding and delta filtering. Do not enable compression by default for tiny high-frequency packets; measure first.

Failure
Expected behavior
Host closes tab
Heartbeat expires, backend increments epoch, grants new host, new host resumes from latest checkpoint/keyframe.
Host goes to background
Host yields when possible; heartbeat fallback handles suspension.
Stale host keeps sending
Packets carry old hostEpoch and are ignored.
Client misses deltas
Interpolation extrapolates briefly; periodic keyframe repairs state.
Client joins mid-workflow
Full state includes behavior state/ticks needed to render the current workflow.
Invalid physics value / NaN
Host catches and quarantines entity; backend rejects malformed checkpoints; recover item from last valid state or configured spawn.

Client is blocked from room simulation until it has a compatible item definition/protocol version.

Freeze shared realtime state and reconnect. Do not continue divergent local canonical simulation.

Last host dies without final leave

Decision
Reason
One client canonical simulation host
Avoids server physics cost and avoids multi-peer conflict resolution.
Backend-controlled host lease
Prevents split-brain state publishers.
WebSocket first
Fastest path to a reliable, observable implementation.
WebRTC as transport adapter later
Potential bandwidth/latency benefit without tying gameplay to WebRTC complexity.
Rapier physics separate from Pixi rendering
Clear responsibilities and good fit for sprite + collider requirements.
Behavior event/command boundary
Makes complex developer-authored workflows testable and serializable.
Environment fields outside item behavior
Keeps canvas physics reusable and items portable.
Server-authoritative durable ownership
Client-host physics does not grant edit rights.
Room sleeps when empty
No background compute; reconnect starts from stable idle state.
